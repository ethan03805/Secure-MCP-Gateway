### FR-22 ContextForge integration (planned, v1.3.0)

TEXT: The owner decided on 2026-10-18 to integrate IBM ContextForge (`github.com/IBM/mcp-context-forge`, Apache-2.0) so that users get real MCP servers: (a) **catalog import**, where an operator browses the ContextForge catalog and imports entries into the Trusted MCP Server Library, and (b) a **bundled ContextForge** instance that runs as a contained, loopback-only backend through which imported hosted servers are reached. Every requirement in this section is planned for release v1.3.0 (Section 2.8). None is part of the requirement set of the current release. The ContextForge facts these requirements rest on (release v1.0.11 of 2026-09-28, the `mcp-catalog.yml` format, the configuration keys, the cosign signing of `ghcr.io/ibm/mcp-context-forge` and the 2026 security advisories) are cited as `CF:` and were read on 2026-10-18. A Gateway-held OAuth 2.1 client for hosted entries that need OAuth is planned for v1.4.0 (FR-22.45); until then FR-22.3 classifies those entries `unsupported`. Not scheduled for any release and recorded as future work (ARCH OD-17): federation with remote ContextForge instances and ContextForge's REST and gRPC tool wrapping.

TEXT: Owner decisions of 2026-10-18, taken after the ContextForge spike (`docs/contextforge-spike.md`): (1) the SEC 3.1 and SEC 3.2 gap for hosted servers is accepted on the terms of SR-3-6 (a recorded trust decision, every tool `untrusted`, risk class `moderate` or higher), and the narrowed probe of SR-3.5-2 is accepted instead of a full SEC 3.5 quarantine; the Security Limitations document states both (FR-22.42); (2) the southbound Streamable HTTP client (FR-5.28 to FR-5.30) returns from the deferred set into v1.3.0, since FR-22.36 depends on it; (3) a Gateway-held OAuth 2.1 client is scheduled for v1.4.0 (FR-22.45) and v1.3.0 keeps OAuth entries `unsupported`; (4) the bundled ContextForge instance is opt-in, not opt-out (FR-22.22, FR-22.44), and the starter set applies only when it is enabled (FR-22.17); (5) federation with remote ContextForge instances and REST and gRPC wrapping stay unscheduled future work.

TEXT: Terms used below. A **local entry** is a catalog entry that names a repository and an install command for a self-hosted server. A **hosted entry** is a catalog entry whose `url` is a remote HTTPS MCP endpoint and that names no install command. A **hosted package** is a signed package built from a hosted entry; its manifest names the hosted endpoint in an `upstream` member that only the bundled ContextForge instance serves (manifest_version 2). The **bundled instance** is the one ContextForge process or container that the ContextForge Connector (E-36) runs. The **release lock** is `packaging/contextforge.lock.json` of the Gateway release.

@FR-22 | ContextForge integration
P: —
S: The Gateway release SHALL let an operator import servers listed in the IBM ContextForge catalog into the Trusted MCP Server Library under the same packaging, signature, provenance, sandbox and policy checks as any other package, and SHALL provide a bundled, contained ContextForge instance through which imported hosted servers are reached, with every tool call mediated by the Gateway.
A: E-36; E-13; E-15; F-107; F-108; F-109; X-19; X-20
V: Analysis | Review the verification results of every FR-22 child requirement and of SR-3-6, SR-3.2-2, SR-3.5-2, SR-3.6-2, SR-3.8-2, SR-4-3, SR-4.5-4, SR-4.7-3, SR-2.10-2, SR-2.13-5, SR-5.6-3 and SR-6.18-2; confirm each has passed.
SRC: OWNER (2026-10-18: integrate IBM ContextForge; catalog import into the Library; bundled ContextForge with the Gateway authoritative; opt-out possible, changed to opt-in on 2026-10-18; federation with remote ContextForge instances out of scope); ARCH §4 E-36; ARCH §18.11
R: The reference packages give four servers. The ContextForge catalog lists about 135 real servers; importing them through the Library keeps one admission path, and the bundled instance gives hosted servers a contained place to run without letting an agent reach them except through the Gateway.
TARGET: v1.3.0

@FR-22.1 | Catalog source
P: FR-22
S: The ContextForge Connector (E-36) SHALL read the ContextForge catalog only from the `mcp-catalog.yml` of the ContextForge release pinned in the release lock, after verifying its SHA-256 against the lock, or from an operator-supplied catalog file whose SHA-256 the operator confirms, and SHALL NOT fetch a catalog over the network while the Gateway runs.
A: E-36; F-107; X-19
V: Test | List the catalog from the pinned file, from a pinned file with one byte changed, and from an operator file with and without the confirmed digest, with outbound network access blocked; confirm the first and the confirmed operator file load, the others are refused with `CATALOG_DIGEST_MISMATCH`, and no network connection is attempted.

R: A catalog that can change under the operator after review would let a third party alter what an import proposes. ContextForge's catalog is a YAML file in its release, so it can be pinned like any artifact.

@FR-22.2 | Bounded catalog parsing
P: FR-22
S: The ContextForge Connector (E-36) SHALL parse a catalog file of at most 4 MiB and 2,000 entries as YAML without anchors, aliases, tags or merge keys, SHALL bound every string field to 4,096 characters, and SHALL refuse the whole file when any bound or rule is violated.
A: E-36; F-107; X-19
V: Test | Load catalogs that exceed each bound and catalogs using an alias expansion ("billion laughs"), a custom tag and a merge key; confirm each is refused within 1 second with the violated rule named and the Gateway's memory use rises by less than 64 MiB.
SRC: CF: `mcp-catalog.yml` (135 entries in v1.0.11); SEC 7.11
R: The catalog is untrusted input (X-19). YAML expansion attacks and oversized fields are the cheapest ways to exhaust a parser.

@FR-22.9 | Hosted entry probe

@FR-22.10 | Hosted package manifest
P: FR-22
S: The ContextForge Connector (E-36) SHALL write a hosted package manifest of manifest_version 2 whose `upstream` member names the kind `contextforge-hosted`, the hosted URL and transport, the catalog entry ID and its digest, and the ContextForge gateway name and slug used for the package (fixed at the probe and reused at every registration), and whose tools, schemas, description digests and `tools_list_sha256` equal the probed tool list, with every tool's `source_trust` set to `untrusted` and the risk class set to `moderate` or higher. Each tool SHALL carry both its manifest `name` (`[A-Za-z0-9_]{1,47}`, Appendix J) and its `backend_name`, the name ContextForge serves (`<gateway-slug>-<original-name>`), where the manifest name is derived deterministically: remove the `<gateway-slug>-` prefix, replace every character outside `[A-Za-z0-9_]` with `_`, and, for every tool whose result is longer than 47 characters or equal to the result of another tool of the same package, use the first 38 characters followed by `_` and the first 8 hexadecimal digits of the SHA-256 of the `backend_name`. The Connector SHALL refuse the import, naming the tools, when two manifest names are still equal, and the Tool Dispatcher (E-10) SHALL send the `backend_name` recorded for the called tool.
A: E-36; E-13; E-10; F-107; F-34; F-23; X-02
V: Test | Probe a fixture hosted server whose tools include `get-time`, a 60-character name and a name with a dot, and validate the written manifest against the manifest_version 2 schema; confirm the members, that tools equal the probed list, that every `source_trust` is `untrusted`, that an operator choice of `low` is refused, that each manifest name matches `[A-Za-z0-9_]{1,47}` and equals the derivation above, that probing the same tools in reverse order yields the same names, that a call to each tool reaches the fixture under its `backend_name`, and that a fixture whose two names still collide after the derivation, or that ContextForge serves under one name (such as `get-time` and `get_time`), is refused naming them.
SRC: SEC 3.7; SEC 3.11; SEC 5.13; ARCH §2.2 A-11; CF: tool names `<gateway-slug>-<original-name>` (`GATEWAY_TOOL_NAME_SEPARATOR`, default `-`), observed in `docs/contextforge-spike.md`
R: Output from a remote service the operator cannot inspect is untrusted content, so the session-taint rule (F-99) applies to every tool it serves. The ContextForge spike (2026-10-18) found that ContextForge serves tools as `<gateway-slug>-<original-name>` with hyphens, that the slug follows the gateway name, and that the Gateway's public names turn hyphens into underscores, so `a-b` and `a_b` would collide and a long slug would push names past the 47-character limit of Appendix J. Recording a mapping derived only from the names themselves (not from their order) makes the manifest name stable across probes and independent of the slug length, the collision check makes an ambiguous mapping an import failure instead of a misroute, and fixing the gateway name in the manifest lets reconciliation treat any rename as drift (FR-22.33). The first hosted-import run against v1.0.11 (2026-10-19) found that ContextForge itself serves `get-time` and `get_time` of one server under the same name (it turns underscores into hyphens in the served name), so two such tools cannot be told apart behind ContextForge; the verification therefore probes them as a refused case instead of expecting two names.
TARGET: v1.3.0
