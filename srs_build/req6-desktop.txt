## 6. Requirements planned for later releases

TEXT: The requirements of this section are planned for the release named in each record's **Target release** field (Section 2.8). They are complete requirements, allocated and verified like the others, but they are not part of the requirement set of the current release: Appendix I counts them separately, the matrices mark them, and the requirement report lists them as planned instead of unverified until a test or record verifies them. Security requirements for planned elements are kept here with their functional requirements, under the same `SR-<SEC id>-k` IDs and parent rules as Section 5.

### FR-20 Desktop application and platform installers

TEXT: Owner decision of 2026-10-18: the product gets a desktop application and native installers so that a person can install, run and operate the Gateway without a terminal. The Desktop Application (E-34) is a Tauri 2 tray application for macOS, Linux and Windows; the Platform Installers (E-35) are a macOS `.pkg` and `.dmg`, Linux `.deb`, `.rpm` and AppImage packages, and a Windows `.msi`. Installers are verified with the project's minisign signature, Sigstore bundle and SHA-256 checksums; platform code signing, notarization and MSIX are deferred (Appendix N) and are additive when enabled. The Windows runtime of `smcpd` itself (host versions, service, directories, listeners and the "not enforced" label) is FR-21 (FR-21.1, FR-21.5, FR-21.6, FR-21.8, SR-4-2); this section relies on it for Windows and does not restate it. The desktop application holds no more authority than the console: every control-API operation is performed in the console window under the user's own console sign-in.

@FR-20 | Desktop application and platform installers
P: —
S: The Gateway release SHALL include the Desktop Application (E-34) and the Platform Installers (E-35) specified by the requirements of this section.
A: E-34; E-35; F-100; F-105; X-16; X-18
V: Analysis | Review the verification results of every FR-20 child requirement; confirm each has passed on macOS arm64, on Ubuntu x86_64 and on Windows 11 x86_64.
SRC: OWNER (desktop app and automated installers on all three platforms, 2026-10-18)
R: A user-friendly product starts from an installer the user already knows how to run and an icon the user can click. The terminal remains supported; it stops being required.
TARGET: v1.3.0

@FR-20.1 | Desktop application platforms
P: FR-20
S: The Desktop Application (E-34) SHALL be built with Tauri 2 from source in the Gateway repository and SHALL run on macOS 14 or later on arm64 (WKWebView), on Linux x86_64 and arm64 with WebKitGTK 4.1 and a system tray that implements the StatusNotifierItem or AppIndicator protocol, and on the x64 Windows hosts of FR-21.1 (WebView2), where it controls the Windows service of FR-21.6. On macOS the application SHALL be built for arm64 only, with no x86_64 or universal build; the command-line archives keep their darwin-amd64 build (Section 1.6).
A: E-34; F-100; X-07
V: Test | In CI, build the application on GitHub-hosted macOS arm64, Ubuntu 24.04 x86_64 and arm64, and Windows x86_64 runners; on each, start it against a running Gateway and confirm the tray icon appears and the console window opens.
SRC: OWNER (Tauri v2 tray app on macOS, Linux and Windows; desktop application macOS arm64 only, 2026-10-18)
R: One code base for three desktops. Tauri uses the operating system's webview, so the application adds no browser engine of its own to patch, and its Rust core is memory-safe like the Go daemon. Owner decision of 2026-10-18: the macOS application targets Apple silicon only; Intel Macs keep the terminal path (the darwin-amd64 archive and `install.sh`), which needs no second application build to test and support.
TARGET: v1.3.0

@FR-20.3 | Service control
P: FR-20
S: The Desktop Application (E-34) SHALL start, stop and restart the installed `smcpd` service only through the platform service manager (the launchd user agent on macOS, the systemd user or system unit on Linux, the Service Control Manager on Windows), SHALL request operating-system elevation only for a system-wide service, and SHALL report within 30 seconds whether the operation succeeded together with the service manager's error text when it did not.
A: E-34; F-100; X-07
V: Test | On each platform, start, stop and restart the service from the menu; confirm the service manager's state after each and the reported outcome; make the unit fail to start and confirm the error text is shown within 30 seconds; on a Linux Enforced host confirm one polkit prompt per operation and none for a user unit.
SRC: OWNER (start/stop/status of smcpd)
R: Stopping the service is not the emergency stop. The emergency stop (FR-3) refuses calls while the Gateway keeps its evidence path running and is done in the console, signed in; service control only starts and stops the process.

@FR-20.8 | First-run setup
P: FR-20
S: When no Gateway configuration exists, the Desktop Application (E-34) SHALL offer a setup window that collects the Administrator and Approver passwords, runs `smcpctl install` for the selected profile, which performs the `smcpctl bootstrap` step before it installs the service, with the passwords passed in files of mode 0600 that it deletes when the command ends, and SHALL show the outcome of the bootstrap step and of the service installation and, when a step fails, its output and the command the user can run in a terminal to retry it.
A: E-34; F-103; I-42; F-97
V: Test | On clean macOS, Ubuntu and Windows runners, complete the setup; confirm the configuration, keys and service exist as after the terminal procedure (FR-13.6), that no password appears in any process argument list (sampled every 100 ms during setup) or remains in a file afterwards; inject a failing install and confirm the output and retry command are shown.
SRC: OWNER (first-run setup wraps smcpctl bootstrap/install); SEC 7.5
R: The setup is a front end to the verified terminal procedure, not a second implementation of it, so FR-13 keeps verifying the installation itself. Process argument lists are readable by other local accounts. `smcpctl install` runs the bootstrap step itself into the CP-46 layout; a separate `smcpctl bootstrap` first would write the configuration and keys into a different directory, and `smcpctl` reads only one password from standard input, so both passwords go in files.

### Security requirements for the desktop application and installers

TEXT: Parents are the MUSTs of `MCP_Gateway_Security_SRS.md` whose controls the desktop application or the installers could weaken. They keep the desktop application at or below the authority of a signed-in console user and keep installed code out of the agent's reach.

@SR-2-3 | Desktop authority ceiling
P: SEC-2
S: The Desktop Application (E-34) process SHALL NOT read the operator token, the Secret Vault, the key store, the Evidence Journal or the password hashes in the configuration, SHALL send no request to the control API itself, and SHALL perform control-API operations only inside the console window under the user's console session, its child processes being limited to the `smcpctl` operations of FR-20.8 to FR-20.12, the platform service manager, the `cosign` check of SR-7-2 and the verified installer that FR-20.13 starts (with `pkexec` for a Linux package).

SRC: SEC 2; OWNER (the desktop app gets no more privilege than the console)

@SR-2.8-5 | Desktop TLS validation
P: SEC-2.8
S: The Desktop Application (E-34) SHALL accept the console window's connection to the admin listener only when the listener presents a certificate that chains to the Gateway server CA of the installation and names the configured host, SHALL show an error page instead of console content otherwise, and SHALL offer no option to proceed past a certificate error.
A: E-34; F-102; I-41; X-04
V: Test | Point the console window at a test listener presenting a certificate from another CA, an expired certificate and a certificate for another name; confirm an error page with no console content and no proceed option in each case; confirm the installation's own listener loads.
SRC: SEC 2.8
R: The console window carries an administrator session; a loopback listener impersonated by another local process must not receive it. Implementation (owner decision of 2026-10-18, strict): the application verifies the listener's certificate chain itself in the webview's certificate hook, with the installation's Gateway server CA bundle (`tls/ca.crt` in the state directory, a public file) as the only trust anchor and the configured host as the required name: the server-trust authentication challenge of the WKWebView navigation delegate on macOS, which it answers for the admin listener's host and port only and cancels for every other host; `load-failed-with-tls-errors` together with a check of the TLS information of every committed load in WebKitGTK on Linux; and the WebView2 `ServerCertificateErrorDetected` event with the same committed-load check on Windows. A loopback proxy in front of the listener was rejected: it would give the console window another origin, which SR-2.9-4 forbids, or would have to rewrite the Origin and Host headers the console checks.

@SR-4.11-2 | Installed code outside the agent's reach
P: SEC-4.11
S: The `.pkg`, `.deb`, `.rpm` and `.msi` Platform Installers (E-35) SHALL install the Gateway binaries and the Desktop Application owned by root (macOS, Linux) or with Administrators-only write access (Windows), not writable by the installing user, and `smcpctl doctor` SHALL report a Gateway binary or application bundle that the user running it can write, which includes the `.dmg` and AppImage forms.
A: E-35; F-106; E-33; F-98; X-18
V: Test | Install each of the four packages; confirm owner and modes (macOS, Linux) or ACLs (Windows) of every installed file and that a write as the installing user fails; install from the `.dmg` and the AppImage and confirm `smcpctl doctor` reports the writable binaries.
SRC: SEC 4.11
R: An agent runs as the user. If it can replace `smcpd` or the desktop application, it can remove every control; the system packages put the code beyond its write access, and doctor says when the drag-install forms do not.
TARGET: v1.3.0

@SR-7-2 | Verified updates
P: SEC-7
S: The Desktop Application (E-34) SHALL start a downloaded installer or upgrade only after verifying the release checksum file's minisign signature with the release public key embedded in the application at build time (the key of `SECURITY.md` and `install.sh`), the installer's SHA-256 against that file and, when `cosign` is installed, the checksum file's Sigstore bundle against the release workflow identity, and SHALL refuse an installer whose version is not newer than the installed one, installing nothing and naming the failed check when any check fails.
A: E-34; F-104; X-16
V: Test | Through a test feed, offer an installer with a modified byte, a checksum file with a modified line, a checksum file signed by another key, a bad Sigstore bundle with cosign installed, and an older correctly signed release; confirm each is refused with the failed check named and nothing installed; confirm a correct newer release is verified and started.
SRC: SEC 7; SEC 10.7; OWNER (update verification uses the release key)
R: An update channel is a code-execution path into the operator's machine. It must trust exactly the key and workflow identity that the other install paths trust, and never accept a rollback to a release with known flaws.
TARGET: v1.3.0
