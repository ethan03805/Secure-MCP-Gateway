## 6. Requirements planned for later releases

TEXT: The requirements of this section are planned for the release named in each record's **Target release** field (Section 2.8). They are complete requirements, allocated and verified like the others, but they are not part of the requirement set of the current release: Appendix I counts them separately, the matrices mark them, and the requirement report lists them as planned instead of unverified until a test or record verifies them. Security requirements for planned elements are kept here with their functional requirements, under the same `SR-<SEC id>-k` IDs and parent rules as Section 5.

### FR-20 Desktop application and platform installers

TEXT: Owner decision of 2026-10-18: the product gets a desktop application and native installers so that a person can install, run and operate the Gateway without a terminal. The Desktop Application (E-34) is a Tauri 2 tray application for macOS, Linux and Windows; the Platform Installers (E-35) are a macOS `.pkg` and `.dmg`, Linux `.deb`, `.rpm` and AppImage packages, and a Windows `.msi`. Installers are verified with the project's minisign signature, Sigstore bundle and SHA-256 checksums; platform code signing, notarization and MSIX are deferred (Appendix N) and are additive when enabled. The Windows runtime of `smcpd` itself (service, paths, listeners) is specified separately in `srs_build/req7-windows.txt`; this section relies on it for Windows and does not restate it. The desktop application holds no more authority than the console: every control-API operation is performed in the console window under the user's own console sign-in.

@FR-20 | Desktop application and platform installers
P: —
S: The Gateway release SHALL include the Desktop Application (E-34) and the Platform Installers (E-35) specified by the requirements of this section.
A: E-34; E-35; F-100; F-105; X-16; X-18
V: Analysis | Review the verification results of every FR-20 child requirement; confirm each has passed on macOS arm64, on Ubuntu x86_64 and on Windows 11 x86_64.
SRC: OWNER (desktop app and automated installers on all three platforms, 2026-10-18)
R: A user-friendly product starts from an installer the user already knows how to run and an icon the user can click. The terminal remains supported; it stops being required.
TARGET: v1.3.0

@FR-20.1 | Desktop application platforms
P: FR-20
S: The Desktop Application (E-34) SHALL be built with Tauri 2 from source in the Gateway repository and SHALL run on macOS 14 or later on arm64 (WKWebView), on Linux x86_64 and arm64 with WebKitGTK 4.1 and a system tray that implements the StatusNotifierItem or AppIndicator protocol, and on Windows 10 22H2 or later and Windows 11 on x86_64 (WebView2), where it controls the Windows service defined in `srs_build/req7-windows.txt`.
A: E-34; F-100; X-07
V: Test | In CI, build the application on GitHub-hosted macOS arm64, Ubuntu 24.04 x86_64 and arm64, and Windows x86_64 runners; on each, start it against a running Gateway and confirm the tray icon appears and the console window opens.
SRC: OWNER (Tauri v2 tray app on macOS, Linux and Windows)
R: One code base for three desktops. Tauri uses the operating system's webview, so the application adds no browser engine of its own to patch, and its Rust core is memory-safe like the Go daemon.
TARGET: v1.3.0

@FR-20.3 | Service control
P: FR-20
S: The Desktop Application (E-34) SHALL start, stop and restart the installed `smcpd` service only through the platform service manager (the launchd user agent on macOS, the systemd user or system unit on Linux, the Service Control Manager on Windows), SHALL request operating-system elevation only for a system-wide service, and SHALL report within 30 seconds whether the operation succeeded together with the service manager's error text when it did not.
A: E-34; F-100; X-07
V: Test | On each platform, start, stop and restart the service from the menu; confirm the service manager's state after each and the reported outcome; make the unit fail to start and confirm the error text is shown within 30 seconds; on a Linux Enforced host confirm one polkit prompt per operation and none for a user unit.
SRC: OWNER (start/stop/status of smcpd)
R: Stopping the service is not the emergency stop. The emergency stop (FR-3) refuses calls while the Gateway keeps its evidence path running and is done in the console, signed in; service control only starts and stops the process.
TARGET: v1.3.0

@FR-20.4 | Health at a glance
P: FR-20
S: The Desktop Application (E-34) SHALL read the CP-51 loopback metrics endpoint at least every 5 seconds while the service runs, SHALL show the tray state of FR-20.2 within 10 seconds of a change in the Gateway's health state, emergency stop or pending-approval count, SHALL show `unreachable` when no exposition has been read for 15 seconds, and SHALL show the label `not enforced` beside the state unless the exposition reports the release label `enforced`.
A: E-34; F-100; I-40; X-15
V: Test | Against a running Gateway, change the health state, set and clear the emergency stop and create an approval; confirm each tray change within 10 seconds; stop the metrics listener and confirm `unreachable` within 15 seconds and never `healthy`; confirm the `not enforced` label on a Standalone installation.
SRC: OWNER (health at a glance); ARCH §4 E-34
R: The metrics endpoint needs no credential and carries no arguments, principals or sessions (security review RR-06), so the tray can show health without holding any authority. Stale data must never read as healthy.
TARGET: v1.3.0

Enabling this requirement needs only the listed secrets and a signing step in the release workflow.

@FR-20.30 | Windows Authenticode signing
P: FR-20
S: The release workflow SHALL Authenticode-sign the Desktop Application executable, the Windows Gateway binaries and the `.msi` with SHA-256 and an RFC 3161 timestamp, using either the repository secrets `WINDOWS_CERTIFICATE` (base64 `.pfx` of an OV or EV code-signing certificate) and `WINDOWS_CERTIFICATE_PASSWORD`, or Azure Trusted Signing with `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TRUSTED_SIGNING_ENDPOINT`, `AZURE_TRUSTED_SIGNING_ACCOUNT` and `AZURE_TRUSTED_SIGNING_PROFILE`.
A: E-35; F-105
V: Test | On a release built with the secrets, run `signtool verify /pa /v` on each signed file; confirm a valid chain and timestamp; confirm the FR-20.23 checksums cover the signed files.
SRC: OWNER (platform signing is a later, additive step)
R: A signature names the publisher in the User Account Control prompt and lets SmartScreen build reputation; Smart App Control requires it.
DEFER: Deferred by owner decision of 2026-10-18: the project has no Authenticode certificate yet. @FR-20.31 | Windows MSIX package

### Security requirements for the desktop application and installers

TEXT: Parents are the MUSTs of `MCP_Gateway_Security_SRS.md` whose controls the desktop application or the installers could weaken. They keep the desktop application at or below the authority of a signed-in console user and keep installed code out of the agent's reach.

@SR-2-3 | Desktop authority ceiling
P: SEC-2
S: The Desktop Application (E-34) process SHALL NOT read the operator token, the Secret Vault, the key store, the Evidence Journal or the password hashes in the configuration, SHALL send no request to the control API itself, and SHALL perform control-API operations only inside the console window under the user's console session, its child processes being limited to the `smcpctl` operations of FR-20.8 to FR-20.12 and the platform service manager.
A: E-34; F-100; F-103; I-41; I-42
V: Test | Run the application through every menu item and window under a file-access tracer (`fs_usage` on macOS, `strace -f` on Linux, Process Monitor on Windows) and a loopback capture; confirm no open of the operator token, vault, key, journal or configuration file by the application process, no control-API request from it outside the console window's webview, and no child process other than the listed `smcpctl` operations and the service manager.
SRC: SEC 2; OWNER (the desktop app gets no more privilege than the console)
R: The operator token acts as the Administrator. A tray application that read it would give every user of the desktop Administrator authority without a sign-in and would turn the application into a target.
TARGET: v1.3.0

@SR-2-4 | No stored console credentials
P: SEC-2
S: The Desktop Application (E-34) SHALL keep console session cookies and console passwords out of persistent storage by giving the console window a non-persistent (incognito) web data store, SHALL write setup passwords only to the 0600 files of FR-20.8 for the duration of the command, and SHALL keep any credential it needs to persist only in the operating system's credential store (macOS Keychain, Secret Service, Windows Credential Manager).
A: E-34; F-102; F-103
V: Test | Sign in to the console window, quit the application and search its data directories, the webview data directories and the temporary directory for the session cookie value and the password; confirm none is found; restart and confirm the console asks for a sign-in.
SRC: SEC 2; OWNER (the app never stores console credentials in plaintext)
R: A persisted cookie would let anything that reads the user's profile resume an administrator session within CP-29.
TARGET: v1.3.0

@SR-2-5 | Minimal IPC surface
P: SEC-2
S: The Desktop Application (E-34) SHALL grant the console window no Tauri capability and no IPC command, SHALL list no remote URL in any capability, SHALL grant its bundled windows only the commands their operations need, and SHALL include no shell plugin permission that runs a program or argument not fixed at build time.
A: E-34; F-102; F-103; I-41; I-42
V: Test | Check the capability files, the generated permission manifest and the command registrations in CI and confirm the console window has none, no `remote` entry exists and each command is used by a bundled window; from the console window's script context, invoke each registered command and a sidecar execution and confirm each is refused.
SRC: SEC 2; OWNER (IPC surface minimized)
R: The console renders content that came from servers and agents (SR-6.17-1). If that window could reach the IPC bridge, an injection in the console would become code execution on the desktop.
TARGET: v1.3.0

@SR-2-6 | No remote content in the desktop application
P: SEC-2
S: The Desktop Application (E-34) SHALL load its bundled windows only from assets packaged in the application under a Content Security Policy whose `default-src` is `'self'`, SHALL allow the console window to load and navigate only within the configured admin listener origin, and SHALL load no script, style, font or frame from any other origin in any window.
A: E-34; F-102
V: Test | Inspect the bundled CSP; with a network capture, exercise every window and confirm no request leaves loopback except the update check of FR-20.11; inject a remote script reference into a bundled page in a test build and confirm the CSP blocks it; navigate the console window to another origin and confirm it is refused and opened in the default browser instead.
SRC: SEC 2; SEC 8.8; OWNER (no remote content loaded)
R: A desktop shell that loads remote code inherits the trust of everything it loads.
TARGET: v1.3.0

@SR-2-7 | Desktop elevation limits
P: SEC-2
S: The Desktop Application (E-34) SHALL run as the logged-in user without elevation, SHALL request operating-system elevation (polkit, macOS authorization, User Account Control) only to install, start, stop or remove a system-wide `smcpd` service and to run a downloaded installer, and SHALL name the command and its arguments in the elevation prompt where the platform shows them.
A: E-34; F-100; F-103; F-104; X-07
V: Test | Exercise every menu item and window on each platform; confirm the application process never runs elevated and that elevation is requested only for the listed operations, with the command named in the polkit and macOS prompts.
SRC: SEC 2; SEC 4.1
R: Elevation granted for one fixed command is auditable; an elevated tray application would be root on the desktop.
TARGET: v1.3.0

@SR-2.6-2 | Notifications never approve
P: SEC-2.6
S: The Desktop Application (E-34) SHALL offer no approve, deny or reply action in any notification, SHALL decide no approval itself, and SHALL bring the user to the Approvals view (G-13) only through the console window, where a decision requires a console session of the Approver or Administrator role.
A: E-34; F-101; I-41; X-14
V: Test | Raise an approval notification on each platform; confirm it has no action buttons or reply field; activate it while signed out and confirm the console shows the sign-in page; sign in as an Operator and confirm the decision is refused; sign in as an Approver and confirm the decision succeeds.
SRC: SEC 2.6; SEC 1.18; OWNER (a notification never lets the user approve without the console's authentication)
R: Notification centers are reachable by anyone at the unlocked desktop and by other applications on some platforms; an approval needs an authenticated approver and its binding (SR-1.18-2).
TARGET: v1.3.0

@SR-2.8-5 | Desktop TLS validation
P: SEC-2.8
S: The Desktop Application (E-34) SHALL accept the console window's connection to the admin listener only when the listener presents a certificate that chains to the Gateway server CA of the installation and names the configured host, SHALL show an error page instead of console content otherwise, and SHALL offer no option to proceed past a certificate error.
A: E-34; F-102; I-41; X-04
V: Test | Point the console window at a test listener presenting a certificate from another CA, an expired certificate and a certificate for another name; confirm an error page with no console content and no proceed option in each case; confirm the installation's own listener loads.
SRC: SEC 2.8
R: The console window carries an administrator session; a loopback listener impersonated by another local process must not receive it.
TARGET: v1.3.0

@SR-2.9-4 | No widened origins for the desktop
P: SEC-2.9
S: The Management Console & Control API (E-24) SHALL serve the Desktop Application's console window with the same Origin, Host and `Sec-Fetch-Site` checks it applies to a browser, SHALL NOT accept a Tauri or other custom-scheme origin, and the Desktop Application (E-34) SHALL require no change to those checks or to the console's Content Security Policy.
A: E-24; E-34; F-63; I-41; X-04
V: Test | Send control-API mutations with the origins `tauri://localhost`, `http://tauri.localhost` and `https://tauri.localhost`; confirm each is refused; complete a console mutation from the console window and confirm it carries the admin listener's own origin and passes unchanged checks.
SRC: SEC 2.9; SEC 8.9
R: Allowing the application's own origin would let any page of that origin, including an injected one, make authenticated control-API requests.
TARGET: v1.3.0

@SR-4.11-2 | Installed code outside the agent's reach
P: SEC-4.11
S: The `.pkg`, `.deb`, `.rpm` and `.msi` Platform Installers (E-35) SHALL install the Gateway binaries and the Desktop Application owned by root (macOS, Linux) or with Administrators-only write access (Windows), not writable by the installing user, and `smcpctl doctor` SHALL report a Gateway binary or application bundle that the user running it can write, which includes the `.dmg` and AppImage forms.
A: E-35; F-106; E-33; F-98; X-18
V: Test | Install each of the four packages; confirm owner and modes (macOS, Linux) or ACLs (Windows) of every installed file and that a write as the installing user fails; install from the `.dmg` and the AppImage and confirm `smcpctl doctor` reports the writable binaries.
SRC: SEC 4.11
R: An agent runs as the user. If it can replace `smcpd` or the desktop application, it can remove every control; the system packages put the code beyond its write access, and doctor says when the drag-install forms do not.
TARGET: v1.3.0

@SR-7-2 | Verified updates
P: SEC-7
S: The Desktop Application (E-34) SHALL start a downloaded installer or upgrade only after verifying the release checksum file's minisign signature with the release public key embedded in the application at build time (the key of `SECURITY.md` and `install.sh`), the installer's SHA-256 against that file and, when `cosign` is installed, the checksum file's Sigstore bundle against the release workflow identity, and SHALL refuse an installer whose version is not newer than the installed one, installing nothing and naming the failed check when any check fails.
A: E-34; F-104; X-16
V: Test | Through a test feed, offer an installer with a modified byte, a checksum file with a modified line, a checksum file signed by another key, a bad Sigstore bundle with cosign installed, and an older correctly signed release; confirm each is refused with the failed check named and nothing installed; confirm a correct newer release is verified and started.
SRC: SEC 7; SEC 10.7; OWNER (update verification uses the release key)
R: An update channel is a code-execution path into the operator's machine. It must trust exactly the key and workflow identity that the other install paths trust, and never accept a rollback to a release with known flaws.
TARGET: v1.3.0
