## Planned requirements: Windows platform (FR-21, target v1.3.0)

TEXT: The owner decided on 2026-10-18 that the Gateway (`smcpd`, `smcpctl` and the helper commands) also runs on Windows, next to macOS and Linux, for the desktop app and the automated installers. The desktop app and its installers are specified separately (`srs_build/req6-desktop.txt`); this section specifies the Gateway itself on a Windows host. Every record here carries a target release (Section 2.8): it is planned, is not part of the requirement set of the current release, and does not affect its release label.
TEXT:
TEXT: **Security posture.** A Windows host cannot provide what the Enforced profile relies on: there is no rootless Podman with user namespaces, no seccomp, no AppArmor or SELinux and no nftables on Windows itself. Windows offers different primitives (AppContainer and Less Privileged AppContainer tokens, Job Objects, the Windows Filtering Platform, virtual service accounts and DACLs), which together contain a backend process less completely than the Linux Enforced sandbox: an AppContainer still reads everything granted to ALL APPLICATION PACKAGES (most of `C:\Windows` and `C:\Program Files`), has no system-call filter, and runs the server's interpreter from the host rather than from a pinned image. A Gateway inside WSL2 can run the Linux Enforced stack, but any process of the Windows user can run `wsl.exe -u root`, so the agent-to-Gateway separation depends on the Windows account the agents run under. Every Windows installation therefore claims the Standalone profile and the label "not enforced" (SR-4-2), and refuses high-risk servers (SR-4-1).
TEXT:
TEXT: The health causes (`partially_confined`, `state_acl`, `key_protection`, `pipe_squatted`) and reason codes (`SHELL_LAUNCH`, `PATH_REFUSED`) named below enter Appendix B when the target release implements them.
TEXT:
TEXT: Three Windows installation modes are specified: the **per-user** mode (no elevation; servers run as ordinary child processes, as on macOS), the **machine** mode (a Windows service under a virtual service account; servers contained in AppContainers with Job Object limits and Windows Filtering Platform egress filters), and the **WSL2** mode (the Linux build in a dedicated WSL2 distribution, reached from Windows agents over the loopback listener). In the per-user mode the agents and `smcpd` run as the same account, so an agent can read the Gateway's state whatever its DACL says; DPAPI there protects against copying the state to another account or host, not against the agent. The machine-mode records (FR-21.13, FR-21.14, SR-4.1-3, SR-4.5-3, SR-4.6-2) fix the outcome; the mechanism (who creates AppContainer profiles, loopback exemptions and WFP filters, and with which rights) is confirmed by the spike that `docs/windows-port.md` schedules before the machine mode is built, and a different mechanism with the same outcome is a controlled change.
TEXT:
TEXT: **Relation to FR-20 and FR-22.** The Desktop Application (E-34) and the `.msi` Platform Installers (E-35) for Windows are specified in FR-20 (FR-20.1, FR-20.20): the application and its `smcp-desktop` `.msi` run on Windows 11 x64, and the `smcp` `.msi` with the command-line Gateway runs on every host of FR-21.1. The application controls the service of FR-21.6 and shows the label of SR-4-2. No desktop application is built for Windows on arm64 or qualified on Windows Server in v1.3.0; those hosts use the `smcp` `.msi` or the FR-21.3 zip archive. The bundled ContextForge instance of FR-22 runs on Windows, in every installation mode, as the managed process of FR-22.20 and FR-22.25 inside its own Job Object (FR-21.12) and not in an AppContainer, so the health cause `contextforge_unconfined` applies while it runs, also in the machine mode.
TEXT:
TEXT: Revised on 2026-10-19 after the measured port (`docs/windows-port.md`, #144): the findings listed there under "Requirements in #131 to adjust" are applied, the named-pipe SR is SR-2.8-6 (SR-2.8-5 belongs to FR-20), and Authenticode signing is left to FR-20.30, which already names the secrets.

@FR-21.4 | PowerShell installer verification
P: FR-21
S: The `install.ps1` script SHALL support the invocations `irm <url> | iex` and `powershell -ExecutionPolicy Bypass -File install.ps1`, SHALL download the zip archive for the host architecture, SHALL verify both the minisign signature and the trusted-comment signature of the checksum file with the release public key embedded in the script, using `minisign.exe` or, when that is absent, OpenSSL 3 (for example the one shipped with Git for Windows, with the key wrapped as an Ed25519 SubjectPublicKeyInfo and the BLAKE2b-512 prehash of prehashed signatures), SHALL verify the archive's SHA-256 with `Get-FileHash` against that file and the cosign bundle when `cosign.exe` is installed, and SHALL install nothing when a verification fails or no signature verifier is available.
A: E-24; F-97; X-16
V: Test | On a `windows-latest` runner, run the script by each supported invocation against a release with a modified archive, one with a modified checksum file, one with a modified trusted comment, and with neither verifier on `PATH`; confirm each is refused with nothing written outside a temporary directory; run it against the intact release with each verifier and confirm installation.
SRC: OWNER (2026-10-18: automated installers; install.ps1 verifying like install.sh); FR-13.2; `docs/windows-port.md` finding 5
R: `irm | iex` is the established PowerShell equivalent of `curl | sh`, and the default execution policy (Restricted on Windows 11 clients, RemoteSigned on Server) refuses an unsigned downloaded script run any other way. PowerShell has no built-in Ed25519 verification, so the script needs the same explicit verifier rule as `install.sh`: refuse rather than install unverified.

@FR-21.6 | Windows service management
P: FR-21
S: On Windows, the `smcpctl install` command SHALL install `smcpd` in the per-user mode, without elevation, as a Task Scheduler task registered through the Task Scheduler API with a logon trigger limited to the installing user's SID and restart after a failure, or, when Windows refuses that registration to the user, as an `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` entry with a printed notice that restart after a failure is unavailable; and in the machine mode (`--machine`, elevated) as a Windows service registered with the Service Control Manager under the CP-46 virtual service account, with automatic (delayed) start, an unrestricted service SID and recovery actions that restart the service after the first and second failures.
A: E-24; E-22; F-97; X-07
V: Test | On a `windows-latest` runner, install the per-user mode as a standard (non-administrator) account and the machine mode as an administrator; confirm the task or Run entry, the notice where the fallback applies, the service definition, its account and recovery settings (`sc.exe qc`, `sc.exe qfailure`); end the `smcpd` process and confirm it is restarted where restart applies; reboot a machine-mode host (Demonstration on a recorded host) and confirm the service starts before any user logs on.
SRC: OWNER (2026-10-18 Windows decision); FR-12.5; FR-13.6; `docs/windows-port.md` finding 6
R: `schtasks /create /sc onlogon` refuses a standard user; the Task Scheduler API with a trigger for the user's own SID may be accepted, and the Run key is the fallback that never needs elevation. The Service Control Manager is the Windows counterpart of the systemd system unit, and a virtual service account gives the service its own identity without a password.

@FR-21.7 | Windows stop and shutdown handling
P: FR-21
S: On Windows, `smcpd` SHALL treat a Service Control Manager stop or preshutdown request and a console `CTRL_C` or `CTRL_BREAK` event as the orderly stop that SIGTERM triggers on Linux, stopping dispatch, recording the stop in the Evidence Journal, terminating every backend instance and exiting within the CP-47 health-wait bound; on a `CTRL_CLOSE`, `CTRL_LOGOFF` or `CTRL_SHUTDOWN` event it SHALL record the stop in the Evidence Journal first and exit within 4 seconds, leaving the backends to the kill-on-close of their Job Objects (FR-21.12).
A: E-12; E-15; E-21; E-24; F-40; F-62
V: Test | Start `smcpd` as a service and as a console process with a running backend; send each stop event; confirm the journal stop record, that no backend process remains and the exit time for each event.
SRC: OWNER (2026-10-18 Windows decision); CP-47; `docs/windows-port.md` finding 7
R: Windows delivers no SIGTERM to a service, and it ends a console process about 5 seconds after `CTRL_CLOSE`, `CTRL_LOGOFF` or `CTRL_SHUTDOWN` whatever the handler does, so the journal record comes first for those events. `smcpctl stop` is the emergency stop, not a process stop, and is not part of this requirement.
TARGET: v1.3.0

@FR-21.10 | Windows key protection
P: FR-21
S: On Windows, the Key & Trust Anchor Manager (E-22) SHALL store each private key file encrypted with DPAPI (`CryptProtectData`, user scope) under the account that runs `smcpd` (the installing user in the per-user mode, the CP-46 virtual service account in the machine mode), SHALL check the state directory DACL of FR-21.5 in place of the POSIX mode check, and SHALL refuse to start with cause `key_protection` when a key file cannot be decrypted, without overwriting it.
A: E-22; F-60; D-08; X-07
V: Test | Install each mode; confirm every private key file is a DPAPI blob; copy the state directory to a second runner and start `smcpd` there; confirm the refusal and that the copied files are unchanged; confirm a normal start on the original host.
SRC: OWNER (2026-10-18 Windows decision: DPAPI, CNG or TPM key protection); FR-12.4; `docs/windows-port.md` (the `keys.CheckPrivate` gate refuses on Windows until this requirement)
R: File modes give no protection on Windows and copied files would be usable elsewhere. DPAPI binds the keys to the account and its master key, so copying the state alone is not enough. In the per-user mode the agent runs as the same account and can unprotect them; that is the macOS Standalone posture. Keys sealed by the TPM through the CNG Platform Crypto Provider are left for a later release, as on Linux.
TARGET: v1.3.0

@FR-21.11 | Windows backend launch
P: FR-21
S: On Windows, the Server Runtime Manager (E-15) SHALL launch each backend with `CreateProcess` from the verified executable path with an argument string built by the Microsoft C runtime quoting rules from the manifest's argument vector, SHALL refuse a manifest whose executable is a `.bat` or `.cmd` file or `cmd.exe`, `powershell.exe` or `pwsh.exe`, and SHALL have the backend process in the instance's Job Object before its first instruction runs.
A: E-15; F-38; X-07
V: Test | Enable a package whose arguments contain spaces, quotes, `&`, `|` and `%PATH%`; confirm the backend receives them unchanged and unexpanded; attempt to enable packages whose executable is a `.cmd` file, `cmd.exe` and `pwsh.exe`; confirm refusal with reason `SHELL_LAUNCH`; confirm from the Job Object accounting that the backend's first process belonged to the job from creation.
SRC: OWNER (2026-10-18 Windows decision); SEC 4.8; CVE-2024-24576 class (batch-file argument injection through `CreateProcess`); `docs/windows-port.md` finding 9
R: Windows passes one command-line string, not an argument vector, and runs `.bat` and `.cmd` files through `cmd.exe`, whose own parsing defeats correct quoting. The statement fixes the outcome; `os/exec` cannot resume a suspended child, so the implementation is expected to use `PROC_THREAD_ATTRIBUTE_JOB_LIST`, which places the process in the job at creation.

@FR-21.13 | AppContainer backend containment
P: FR-21
S: In the Windows machine mode, the Execution Sandbox (E-16) SHALL run each backend under the AppContainer profile of its enabled server revision with no capabilities (a Less Privileged AppContainer when the package manifest declares it compatible), created when the revision is enabled, with access granted to that AppContainer SID only on the revision's installed package tree, its scratch directory and the filesystem slots of SR-4.6-2, and the Health & Safety Monitor (E-23) SHALL then report health `degraded` with cause `partially_confined` instead of `unconfined` while every enabled backend runs in an AppContainer.
A: E-16; E-15; E-23; F-41; F-61; I-23; X-07
V: Test | In the machine mode, run the hostile fixtures that read the user's profile directory, write outside their scratch directory, open a TCP connection and open the `smcpd` state directory; confirm each is denied; confirm the health cause with all backends contained and `unconfined` after one backend is enabled without containment.
SRC: OWNER (2026-10-18 Windows decision: AppContainer, Job Objects, restricted tokens); SEC 4.1; SEC 4.6; Microsoft documentation (AppContainer isolation, Less Privileged AppContainer); `docs/windows-port.md` findings 2 and 3
R: AppContainer is the strongest native per-process boundary Windows offers to a third-party service. One profile per enabled revision matches release 1.x, which runs one shared instance per revision (FR-5.10 deferred), and lets the access entries on the package tree be written once at enablement instead of walking tens of thousands of files at every start. It is weaker than the Enforced sandbox (no system-call filter; reads of ALL APPLICATION PACKAGES locations), so the health cause names partial confinement and the label stays "not enforced" (SR-4-2).
TARGET: v1.3.0

P: FR-21
S: In the Windows machine mode, the Egress Broker (E-18) SHALL be each contained backend's only network path: the backend's AppContainer has no network capability, the elevated step that enables a server revision SHALL create the revision's loopback exemption and the Windows Filtering Platform filters of SR-4.5-3 and the uninstall or disable step SHALL remove them, and the broker SHALL serve the backend as an HTTP proxy on a loopback port with the destination checks of FR-5 unchanged.
A: E-18; E-16; F-45; I-25; X-06; X-07
V: Test | In the machine mode, run the hostile egress fixtures (direct TCP to an external address, DNS over UDP, a connection to another loopback port and an allowed and a denied destination through the proxy); confirm only the allowed proxied destination succeeds and each other attempt is blocked and recorded; disable the revision and confirm its exemption and filters are gone.
SRC: OWNER (2026-10-18 Windows decision: Windows Filtering Platform per AppContainer SID); SEC 4.5; Microsoft documentation (AppContainer loopback isolation; WFP ALE connect layer); `docs/windows-port.md` finding 2
R: An AppContainer without the internet capabilities has no network, and AppContainers cannot reach loopback without an exemption. The exemption covers every loopback port and needs an administrator, so it is made when the revision is enabled (an elevated operation in the machine mode), and the WFP filter is what limits the SID to the broker port.
