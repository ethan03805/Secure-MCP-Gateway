# Security review of the v1.3.0 surface

Adversarial review of what v1.3.0 adds to the Gateway, done on 2026-10-20 at main `4b4da34`, in the manner of the [October 2026 review](security-review-2026-10.md). It covers the desktop application (E-34), the installers (E-35), the southbound Streamable HTTP transport (FR-5.28 to FR-5.30), the ContextForge Connector (E-36, FR-22) and the Windows runtime (FR-21). The reviewer took these positions: a process of the user's own account (an agent with a shell), another local account on the same host, a web page in the user's browser, a malicious or compromised MCP server reached over HTTP, a malicious ContextForge catalog file, and a network attacker between the Gateway and a remote server.

Each finding was reproduced on the code path before it was reported, and each fix has a regression test in the same change. Finding IDs continue the numbering of the October review. The severity scale is the same: **Critical** (remote compromise without credentials), **High** (compromise or data exposure from a position the threat model admits), **Medium** (denial of service from an unauthenticated position, privilege gained under a second condition, secret exposure that needs a second condition), **Low** (defense in depth, information exposure of little value).

No critical or high findings.

## Findings

| ID | Severity | Location | Finding | Status |
|---|---|---|---|---|
| SR-18 | Medium | `desktop/src-tauri/src/setup.rs`, `lib.rs` (`setup_get`, `setup_run`) | First-run setup of the Enforced profile runs `pkexec <smcpctl> install ...`, where `<smcpctl>` is the first of: beside the application's executable, `/usr/local/bin`, `/usr/bin`, `/opt/homebrew/bin`, `~/.local/bin`. The path was not checked for who can change it. When the application runs from a build or download directory (not from the `.deb` or `.rpm`, which install it in `/usr/bin` beside the packaged `smcpctl`) and `smcpctl` is found beside it or in `~/.local/bin` (where `install.sh` puts it), a process of the user, such as an agent, can replace that file before the polkit prompt, and the user's approval then runs the agent's program as root. The Enforced profile exists to keep the agent from changing the Gateway, so this defeats it. | Fixed: `setup::elevation_safe` resolves the path and requires the file and every directory above it to be owned by root and writable by no other account (group write only for group root). The setup window offers the Enforced profile only for such a copy and names the missing prerequisite otherwise; `setup_run` checks again and passes the resolved path to `pkexec`. Test: `setup::tests::elevation_only_runs_a_root_owned_smcpctl` (pull request 202). |
| SR-19 | Low | `internal/winpipe/winpipe_windows.go` (`Listener.Accept`) | The harness named pipe is created with `FILE_FLAG_FIRST_PIPE_INSTANCE`, so a pipe someone else created first is refused (`pipe_squatted`). Later instances are created without the flag, as Windows requires, and only when the next `Accept` starts. A pipe name exists only while an instance is open, so between a served instance being closed (immediately, for a client whose identity cannot be read) and the next `Accept`, no instance held the name. Another account that created the name in that moment with its own security descriptor would have had the listener's next instance join its pipe, and harness clients could connect to the other account's instance and send it their `uds_key` and tool calls. The window is short and the DACL keeps the other account from connecting, so it cannot open the window itself. | Fixed: `Accept` creates the instance the next `Accept` serves while the served instance still holds the name, so the name is held from `Listen` to `Close`. Because the instance now exists before `Accept` waits on it, a client can open it and leave first; `Accept` then frees the instance and waits again instead of returning an error, which would end the listener. Test: `TestWindowsPipeNameHeldBetweenAccepts` (Windows job), which closes a served connection, fails to create the name with `FILE_FLAG_FIRST_PIPE_INSTANCE`, and then has a client leave before `Accept` and the next client served. |
| SR-20 | Low | `cmd/smcpctl/install_machine_windows.go` | `smcpctl install --machine` took `%ProgramFiles%` and `%ProgramData%` from the environment variables of the elevated process. A user's environment includes the variables of `HKCU\Environment`, which a process of that user can set, so the folders of the service binary and of the state could be chosen by the agent before the user runs the elevated install. This review did not confirm on a Windows host which value wins over the system definition; the code path reads the variables. | Fixed as defense in depth: both folders come from `KnownFolderPath` (`FOLDERID_ProgramFiles`, `FOLDERID_ProgramData`) through `winsvc.ProgramFiles` and `winsvc.ProgramData`. Test: `internal/winsvc.TestMachineFoldersIgnoreEnvironment` (Windows job). |
| SR-21 | Low | `internal/southbound/sse.go` (`sseReader.Next`) | Found by `FuzzSSEReader`. The line feed that joins two `data` lines of a Server-Sent Event was not counted against the message bound, so the prefix of an oversized event could be one byte longer than the bound. The event was still marked oversized and withheld (`-31003`), so no oversized content reached the dispatcher. | Fixed: the joining line feed counts against the bound. The fuzzer's input is kept as a regression seed (`internal/southbound/testdata/fuzz/FuzzSSEReader`). |

## Residual risks

Not fixed in this review. Each one is stated in [security-limitations.md](security-limitations.md).

| ID | Severity | Location | Risk | Recommendation |
|---|---|---|---|---|
| RR-13 | Medium | `internal/winpipe` (`Dial`), `internal/adapter` (`RunUDS`) | A harness client does not check who created the pipe it opens. While the Gateway is not running, another local account can create `\\.\pipe\smcp-harness` (machine mode) or `\\.\pipe\smcp-harness-<SID>` (per-user mode); a client that connects sends it its `uds_key` and tool calls and accepts its results. The key alone does not let that account use the Gateway, which also checks the client's SID, and the client allows identification only, never impersonation. When the Gateway starts after the squatter, it refuses the pipe and reports `pipe_squatted`. | Check the pipe's owner, or the server process's account, in `winpipe.Dial` before the first write. Not done here: the expected owner differs between the per-user mode, an elevated start and the machine-mode virtual account, and needs runs on a Windows host to get right. Until then, keep the Gateway running while clients are configured, and check `smcpctl health` for `pipe_squatted`. |
| RR-14 | Low | `internal/contextforge/bundle` (`Instance.run`) | The bundled ContextForge credentials (its JWT key among them) are passed to the container as environment values, so they are not on a command line or in a file, but the container engine records them in the container's configuration: `podman inspect` or `docker inspect` shows them to anyone who can use the engine. With rootless Podman that is the user's own account, which in the Standalone profile can already read the instance's memory (CF-R4). With Docker it is every member of the `docker` group, which is equivalent to root. | Prefer rootless Podman. A credential file mounted read-only from a private directory would keep the values out of `inspect`, at the cost of a file the vault does not hold. |
| RR-15 | Low | bundled ContextForge with Docker Engine | The instance's port is published on `127.0.0.1` only (FR-22.26). Docker Engine releases before 28.0 did not drop packets that other hosts on the same network segment send to a port published on `127.0.0.1`; Docker Engine 28.0 drops them. Every route except `/health` and `/ready` needs a token only the Gateway holds. | Use Podman or Docker Engine 28.0 or later. |
| RR-16 | Low | `desktop/src-tauri/src/installer.rs` (Linux update) | A verified `.deb` or `.rpm` reaches `dpkg` or `rpm` as a sealed in-memory copy that no process can change. On a host where a process may attach a debugger to another process of the same user (`kernel.yama.ptrace_scope` set to 0), an agent can change the running desktop application itself, and through it what is installed. | Accepted: the same access already lets such a process act as the user. Set `ptrace_scope` to 1 or more, or update from a terminal with `install.sh`. |
| RR-17 | Low | `internal/keys/protect_windows.go` (`WriteMachineOperatorToken`) | In the Windows machine mode a copy of the operator token is protected with machine-scope DPAPI, which any account on the host can decrypt, so that `smcpctl` run by an Administrator can use the control API. Only the file's protected DACL (SYSTEM, Administrators, the service account) keeps other accounts from it. | Accepted by the spec owner on 2026-10-20: Administrators already control the service. |
| RR-18 | Low | macOS and Windows desktop updates | The time between the application's last SHA-256 check of a downloaded `.pkg`, `.dmg` or `.msi` and the installer reading it (security limitation 14, unchanged). | Unchanged until the installers are signed (FR-20.29, FR-20.30, blocked on certificates). |

## Areas reviewed without findings

- **Tauri capabilities and commands.** `withGlobalTauri` is off, `freezePrototype` is on, the bundled windows have a CSP without inline script or remote origins, and each bundled window has one capability file naming its own commands only. The console window (`console`) is in no capability file, so the console page, served by `smcpd`, can call no command; every command also checks the calling window's label (`only_window`). The shell and updater plugins are not linked; processes are started only with fixed argument vectors (a test refuses `Command::new` in `lib.rs`). Client setup runs `smcpctl connect` only for a client ID that detection listed and after a preview of the same ID and lockdown choice.
- **Deep links.** Only `smcp://console`, `smcp://approvals` and `smcp://approvals/<UUID>` are accepted, by exact case-sensitive comparison, with a 64-byte limit before parsing; a query, fragment, user information, port or other path is ignored. An accepted link only opens a console page, where the user signs in and decides; the approval ID is rebuilt from its parsed bytes before it reaches a URL.
- **Console window.** Non-persistent web data store, no developer tools, navigation only within the admin listener's origin (scheme, host and port), other http and https pages handed to the default browser, every other scheme refused, new windows denied.
- **CA pinning.** macOS: the navigation delegate's challenge handler trusts only a chain that `tlspin::verify_chain` accepts against the Gateway CA for the configured host and port and cancels every other server-trust challenge. Linux: a TLS error is overridden only for the admin listener after the same check, and every committed https load is checked against the Gateway CA through the page's TLS information, so the system trust store never decides alone. Windows: there is no WebView2 hook yet, and the console window fails closed with the bundled error page.
- **Setup passwords.** Two files of mode 0600 in a new directory of mode 0700 (created with `create_new`, never through an existing name), overwritten and removed when `smcpctl` ends, never in an argument list (the Linux end-to-end test reads process argument lists every 100 ms); the `Secret` type zeroes its memory and never prints.
- **Updater.** The minisign signature with the embedded release key (prehashed signatures only), a trusted comment that must name the checksum file and so the version, a version strictly newer than the installed one, release asset names of one plain path segment, files refused before download unless listed in the verified checksum file, and the Sigstore bundle when cosign is installed. `pkexec`, `dpkg`, `rpm`, `open` and `msiexec` are fixed absolute paths.
- **Installers.** The `.pkg` has no scripts; the `.deb` and `.rpm` have one maintainer script, which runs `/usr/bin/smcpctl uninstall --package-removal` on removal only; the `smcp` `.msi` is per-machine with no custom actions, so its files take the `Program Files` access control list. `install.ps1` verifies the minisign signature (with minisign or OpenSSL 3, including the trusted comment), the archive's SHA-256 against the verified checksum file, and the Sigstore bundle when cosign is installed, in a per-run temporary directory, before it copies anything.
- **Southbound Streamable HTTP.** http only to loopback hosts; no proxy, no redirects (the token goes only to the configured URL); a bearer token and a session ID of visible ASCII only; `x-mcp-header` names must be RFC 9110 tokens and values are encoded (FR-5.29); response bodies and SSE events bounded by the message bound, response headers by 64 KiB; resumption at most three times with the server's retry delay capped at 5 s. The address guard runs on the address actually dialed: loopback, link-local, cloud metadata, multicast and unspecified addresses are refused for a URL that does not name loopback. A probe from macOS found that IPv4-compatible (`::7f00:1`), NAT64 (`64:ff9b::7f00:1`), 6to4 (`2002:7f00:1::`) and `0.x.x.x` forms do not reach the host's own loopback services; the IPv4-mapped form, `0.0.0.0` and `::` do and are refused.
- **ContextForge Connector.** The catalog's SHA-256 is checked against the release lock or the operator's confirmation before parsing; the parser refuses anchors, aliases, tags, merge keys, deep nesting, long strings and duplicate IDs; install strings are never executed. The instance's five credentials are 256-bit random values checked against the published defaults, passed to the engine through its environment, never on a command line, and removed from engine output before it is logged. The container runs read-only with all capabilities dropped, `no-new-privileges`, memory, CPU and process limits, published on `127.0.0.1` only. Each hosted package has its own non-admin user, team and virtual server, a token scoped to that server and valid for one day, and the scope self-check of FR-22.29.
- **Windows runtime.** Pipe DACL (protected, NETWORK and ANONYMOUS LOGON denied, no other SID), `PIPE_REJECT_REMOTE_CLIENTS`, clients that allow identification only, the client SID read from the impersonation token and never from a process ID, and a panic when `RevertToSelf` fails. Job Objects with `KILL_ON_JOB_CLOSE`, no breakaway, UI restrictions and an explicit inherited-handle list; keys as user-scope DPAPI blobs; machine-mode directories with protected DACLs for SYSTEM, Administrators and the service account.
