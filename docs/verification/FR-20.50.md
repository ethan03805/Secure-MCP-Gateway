## Surfaces inspected

Screenshots taken at the commit above, in the light and the dark scheme, and read one by one:

- **Desktop windows**: `node desktop/e2e/a11y.mjs` with `SHOTS` set (WebKit, the engine of WKWebView) wrote 66 window screenshots: the four introduction steps, the status window in each of the seven tray states and the not-enforced degraded variant, the eight setup stages, the six client-setup states and the seven Check for Updates states, each in both schemes. The same run passed axe-core's WCAG 2.2 A and AA rules on every one of them, the CSP check and the reduced-motion check (`desktop/e2e/a11y.mjs:161`).
- **Console**: a Gateway bootstrapped with `smcpctl bootstrap` in a scratch directory (ports 28943 and 28944), signed in as the Administrator in WebKit: G-01 Gateway control, G-02 Policy studio, G-04 Observation workbench, G-11 Sessions and principals and G-13 Approvals.
- **Site**: `npm run build` in `site/`, the static export served locally: the home page and the install page.

## Observations

- **Layout.** Every surface reads top to bottom from one left edge. The console views and the site pages put their data in ruled tables with hairline rules and no cards (`console/src/styles.css:40` for the type scale they share with the desktop windows); the desktop windows are single columns with ruled lists (client setup), definition lists (status, updates) and form sections with a rule after each heading. Nothing is centered except short labels inside buttons. One `h1` per window or view.
- **Color and state.** Each state color comes with a word and a shape: the tray-state line of the status window (diamond and "Degraded" with the `not enforced` box), the console's status strip ("running, not enforced" with its square), the console's table state cells (square and "active", ring and "to do"), and the site's release table, which uses words only. The dark scheme redefines every token; no surface keeps a light background in the dark scheme. Stale state is neutral: the unreachable status window shows the ring in `--ink-3` and "Last reading".
- **Type.** The desktop windows use the five-size scale `--fs-1` to `--fs-5` (`desktop/src/style.css:30` to `desktop/src/style.css:34`), the same values as the console, with IBM Plex Sans and Plex Mono for versions, counts and commands (the Updates window's versions, the setup window's `smcpctl install`). The site uses Newsreader with Plex Mono, as the guide allows for it.
- **Motion.** The desktop stylesheet removes every animation and transition under reduced motion (`desktop/src/style.css:130`), and the a11y run confirmed no step animation with reduced motion emulated.
- **Banned patterns.** None seen: no gradient, blur, glow, text or drop shadow, sparkle or AI glyph, decorative shape, illustration or card grid on any screenshot. Corner radii are 3 px on desktop controls (`desktop/src/style.css:104`), within the 4 px limit, which `tools/uilint` also checks on every stylesheet.
- **Contrast and focus.** axe-core found no contrast violation on the desktop windows in either scheme. The console's focus indicator and contrast are covered by its own Playwright suite (`console/e2e/a11y.spec.ts`), which this inspection did not repeat.

Two notes that do not fail the guide:

- G-11's Principals table is wider than the view at 1,280 px; its wrapper scrolls horizontally and takes keyboard focus (`overflow-x: auto`, `tabindex="0"`), so nothing is cut off. A narrower Action column would avoid the scroll.
- The site's home page opens with the README's paragraph, which says "agent harnesses". The writing guide prefers "agent" in UI text; the site renders the README as documentation, which the writing guide leaves to review (`docs/design/writing.md:16`).

## Deviations

- The inspection was made by an agent reading screenshots, not by a person at the screens.
- The desktop windows were rendered in WebKit as the CI `desktop` job renders them (`desktop/e2e/a11y.mjs`), not inside the running application; the application's windows load the same files.
